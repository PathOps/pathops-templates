# PathOps Templates

Official public Golden Path template catalog for PathOps.

Repository: `PathOps/pathops-templates`.

The catalog is intentionally public. Templates are product scaffolding, not
secrets: users should be able to inspect what PathOps will create before
selecting a template.

## CLI contract

The canonical application-creation command is:

```text
pathops create app --name <name> --template <template-id>
```

`--name` and `--template` are required. The Tenant Control Plane owns the
durable provisioning workflow; the CLI authenticates, submits the request and
reports/resumes its state.

## Initial catalog

Slice 36 starts with exactly one product template:

```text
generic-container
```

It is deliberately technology-agnostic. Its purpose is to prove the PathOps
container/GitOps lifecycle without making Go, Java, Node.js, React or another
framework part of the platform contract.

Later stack-specific templates are convenience scaffolds layered on the same
contract. Users may always start from `generic-container` and modify the
generated repositories freely.

## Repository ownership generated by a template

A template scaffolds three user-owned repositories:

```text
<app>
<app>-gitops-preflight
<app>-gitops-production
```

Responsibilities:

```text
source repository
  source/component tests
  .pathops/build/
    Dockerfile and build-specific files
    editable Tekton pipeline/tasks/scripts

preflight GitOps repository
  preflight desired state
  .pathops/deploy/
  .pathops/tests/

production GitOps repository
  production desired state
  .pathops/deploy/
  .pathops/smoke/
```

`.pathops/` is a transparent placement convention, not a proprietary pipeline
DSL. Generated Tekton/Kubernetes YAML, Dockerfiles and scripts are intentionally
visible and editable. The Application owns them after creation.

The source and environment repositories may evolve independently. For example,
preflight may run PostgreSQL in Kubernetes while production points at a managed
external database; their validation workflows may also differ.

## Catalog layout

```text
templates/
  generic-container/
    template.yaml          descriptor (below)
    README.md              this template's documentation (not copied)
    source/                initial content of <app>
    gitops-preflight/      initial content of <app>-gitops-preflight
    gitops-production/     initial content of <app>-gitops-production
```

## Template format (schemaVersion 1)

The Tenant Control Plane renders a template; the CLI never does. The format is
deliberately the smallest deterministic one `generic-container` needs. Do not
introduce generalized inheritance or an adapter framework until a concrete
second template demonstrates the need.

`template.yaml`:

```yaml
schemaVersion: 1
id: generic-container        # equals the directory name
name: Generic Container
description: ...
inputs: []                   # no user inputs yet
repositories:                # the directory of each repository's content
  source: source
  preflight: gitops-preflight
  production: gitops-production
technology:                  # optional: plain labels the UI shows (Decision 0060)
  runtime: container         # each optional, at most 64 characters
  language: any
  framework: ...
  build: Dockerfile
```

`technology` is declared, never inferred from a repository's content; the
Tenant Control Plane records it with the template's resolution. A Tenant
Control Plane older than this field (before 42be29a53148) rejects a
`template.yaml` that has it.

Rendering:

- every file under a repository's directory becomes that repository's file at
  the same relative path, as the first commit of `main`;
- a file ending in `.tmpl` is rendered and loses the suffix: every
  `{{ name }}` must name a known value and is replaced by it; any other `{{`
  is an error. The only value today is `app.name` (the Application name).
  There are no functions, conditions, loops, includes or inheritance;
- every other file is copied byte for byte (a plain file may contain `{{`);
- failures stop the provisioning: an unknown value, a malformed placeholder,
  two files producing one path, an empty repository directory, a symbolic link,
  a `.git` path, more than 512 files or 4 MiB;
- the generated files are mode 100644 (run scripts with `sh <script>`).

The same catalog commit and Application name always produce the same bytes.

## Resolution

The Tenant Control Plane reads the catalog anonymously from GitHub:

1. the requested ref (`main`) is resolved to a commit through the git
   smart-HTTP ref advertisement;
2. the commit's archive is downloaded (never a branch archive), and
   `templates/<id>/` is extracted;
3. the commit and a `sha256` digest of the template's files are persisted with
   the Application. Every later step fetches the same commit and checks that
   digest.

## generic-container

The initial content is a static page served by BusyBox `httpd` as a non-root
user on port 8080:

- it needs no language, framework or package manager;
- it builds with any OCI builder from `.pathops/build/Dockerfile` (context =
  the repository root);
- it answers `/healthz` for Kubernetes probes and the environment checks.

| Repository | Content |
|---|---|
| `<app>` | `README.md`, `app/` (page, `healthz`), `tests/check-content.sh` (source test), `.pathops/build/` (`Dockerfile`, README), `.pathops/tekton/` (`pipelines/build-and-push.yaml`, `tasks/build-image.yaml`), `.dockerignore` |
| `<app>-gitops-preflight` | `kustomization.yaml`, `deployment.yaml`, `service.yaml`, `README.md`, `.pathops/deploy/`, `.pathops/tests/http-check.sh` |
| `<app>-gitops-production` | the same desired-state files, `README.md`, `.pathops/deploy/`, `.pathops/smoke/http-check.sh` |

The build workflow is `.pathops/tekton/` of the source repository (PathOps
Decision 0056): on every push to `main`, PathOps runs the `build-and-push`
Pipeline, which Tekton Remote Resolution loads with its `build-image` Task from
the source repository at the pushed commit. Every parameter comes from the
PathOps trigger; the files name no Cell. The deploy workflow and the image
reference are added later: until then the desired state names the image
placeholder `<app>`, and nothing deploys.

## Reproducibility

The TCP persists enough provenance to identify exactly what scaffold was used:

- `templateId`;
- catalog source/ref;
- resolved immutable catalog commit SHA (or equivalent revision).

A mutable template name alone is not sufficient provenance. The catalog is
authoritative for creation; generated repositories become authoritative after
creation and are not silently rewritten when the catalog changes.

## Goals

- transparent and editable Golden Paths;
- deterministic/reproducible application bootstrapping;
- GitOps-first environment ownership;
- technology-neutral minimum container contract;
- no application dependency on PathOps-internal implementation products;
- simple enough that users can fork/modify workflows directly.
